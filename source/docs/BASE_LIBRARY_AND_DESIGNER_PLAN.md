## Quality contract: earn a catalog slot

Every family must supply:

1. **A distinct spatial plan.** Different entrances, service placement, district relationships or route topology—not just extra copies of the same yard. Document the difference from its closest existing family.
2. **An explicit composition contract.** Minimum/target roles, budget bounds, supported sizes, physical footprint and required supported assets. Fail clearly if an exact count is infeasible.
3. **A deterministic recipe.** Stable ID, version, seed handling and golden fixtures. Preserve older saved recipes and fixed arrangements.
4. **An honest terrain contract.** Suitable slopes/space, mirrored-team checks when selected, protected regions, adaptation bounds and failure cases. No hidden flattening.
5. **Power and access evidence.** Required service buildings powered under the stated editor rules; readable approaches and preserved entrance constraints. In-game evidence has its own status.
6. **Usable documentation.** Card thumbnail, side/overhead images, purpose, strengths/tradeoffs, editing guidance and known limitations.
7. **Variation evidence.** Proposed initial gate: 12 deterministic seeds per supported size, across flat, valley and irregular fixtures. Record successes and rejections; impossible fits should reject safely, not be counted as successes. Visually compare representative seeds, not only counts.
8. **Round-trip and editing evidence.** Preview has no mutation; apply/undo; save/reopen; portable library export/import; correct retained metadata and original assets.

Release new families in batches of at most six after the library and designer foundations. Inspect spatial diversity before adding another batch. Proposed first new batch: Frontier Camp, Offset Bastion, Service Courtyard, Broken Ring, Valley Pockets and Three-Lane Anchor. This deliberately covers different scales and plans; terrain-dependent entries wait for the necessary designer constraints.

## Base workshop: editing model

| Level | User operation | Required behavior |
| --- | --- | --- |
| Whole base | Set boundary, origin, orientation, team and symmetry policy | Visible placement preview; no forced team pairing for manual work |
| District | Select, group, move, rotate, duplicate, mirror, name and lock | Keep district members and authored internal relationships together; one undoable transaction |
| Building | Place, inspect, pin or precisely edit an original supported structure | Current placement and asset rules remain authoritative |
| Connection | Reserve an entrance, courtyard or route between districts | Constraint is visible and checked; cannot be silently discarded to meet a unit budget |
| Recipe | Set role budgets and randomization permissions | Reroll only eligible parts; retain pinned elements and report infeasible requests |
| Reusable asset | Save fixed base, district or recipe | Distinct types, versioned storage, provenance and portable export |

Useful starting districts: command/uplink, repair and refuel, paired power, close defense, flak defense, missile support and optional Darklight support. Do not introduce missing legacy unit models or invent server mechanics to fill the palette.

### User workflow

Choose a preset or Empty base → outline the build area → choose team/optional mirroring → place a service district → add or edit districts → reserve entrances and movement space → pin important pieces → request three arrangements for the remaining pieces → inspect → Apply → save to My bases.

The manual workflow must remain complete without randomization. A generated layout should be editable with the same tools rather than becoming an opaque special object.

### Proposed persisted records

| Record | Information to preserve |
| --- | --- |
| Library entry | Stable ID/version, name, author/source, description, tags, kind, thumbnails, supported assets and review status |
| Fixed arrangement | Actual original-size units, relative transforms, ground-placement intent, team-remapping policy and anchor |
| District | Membership, local coordinates, role, locks, connection sockets and local keep-out areas |
| Recipe | District graph, role budgets, variation rules, seed/version, adaptation limits and size definitions |
| Constraints | Base boundary, entrances, protected terrain, pinned objects, spacing/power/access assumptions |
| Placement receipt | Map/source revision, chosen parameters, candidate/version, validation results and any game-test reference |

This is a proposed data contract, not an existing import schema. Validate imported values and supported types, preserve unknown old map data through existing map round-trips, and add migrations before changing saved recipe meaning. A fixed favorite must not unexpectedly reroll when opened.
